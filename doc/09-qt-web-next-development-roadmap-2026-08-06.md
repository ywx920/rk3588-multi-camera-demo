# Qt与Web下一阶段开发路线

## 1. 总体原则

下一阶段不再同时修改采集、推理、编码和UI。每个阶段只替换一层，并保留开关和
回退路径。所有性能结论必须同时记录CPU、RSS、输出FPS、推理耗时、端到端延迟、
温度和错误日志，不能只看画面是否出现。

## 2. Qt端开发建议

### Q1：完善性能遥测和状态机压力测试（最高优先级）

实现内容：

- 每路显示采集FPS、显示FPS、推理FPS、覆盖帧数、端到端P50/P95延迟；
- 全局显示CPU、RSS、NPU频率、温度和RGA/RKNN错误计数；
- 自动执行每路及全局Start/Stop 1000轮；
- 退出前等待采集、Scheduler和worker有序结束。

验收：连续1000轮无`waiting for frame`、无残影、无死锁；8小时RSS不持续增长；
关闭窗口后设备节点可立即被Minimal程序打开。

### Q2：RKNN输入内存复用和零拷贝

实现内容：

- 每个worker预分配模型输入tensor memory；
- RGA直接写入固定输入buffer，避免QImage到`rknn_inputs_set`重复复制；
- 显示图与推理输入分离，预览尺寸不再决定模型预处理成本；
- 保留现有复制路径作为运行时回退。

验收：检测框坐标与现版一致；三路CPU下降；推理P95不恶化；无RKNPU/IOMMU fault。

### Q3：UC325硬件MJPEG解码

用MPP JPEG decoder或V4L2硬件解码替代Qt软件解码，再由RGA缩放。必须用保存的
UC325码流做离线回归，并连续验证1000帧颜色、尺寸和时间戳。

### Q4：8路UI与调度准备

- 保留当前2×2为三路默认布局，新增分页或4×2监控模式；
- 永远固定卡片几何，不允许图像内容改变布局；
- Scheduler固定最多3个NPU worker，8路采用最新帧、公平轮询和通道优先级；
- 初始参数：显示8–10 FPS、推理1–3 FPS、工作宽640。

Qt端不建议直接把8路都设置为8 FPS推理，这会增加排队延迟而不一定提高业务效果。

## 3. Web端开发建议

### W1：修复硬件编码链路（最高优先级）

当前软件JPEG是三路订阅时的主要CPU和带宽负担。正确路线：

```text
采集/解码 -> RGA缩放 -> NV12 -> 检测框叠加 -> MPP JPEG或H.264
```

若检测框必须在服务端烧录到画面，可用RGA/DRM overlay或在NV12上绘制；若允许前端
绘框，则视频保持NV12/H.264，检测结果通过WebSocket单独发送，浏览器Canvas叠加。
后者更适合8路。

MPP准入标准：连续解码100帧、SOI/EOI及尺寸正确、浏览器30分钟无坏帧；失败自动
回退Qt JPEG。不能再用“有JFIF头”作为成功标准。

### W2：视频与检测元数据分离

- 视频改用H.264/WebRTC；
- 检测框、类别、置信度、track ID和时间戳走WebSocket；
- 前端Canvas按视频实际尺寸映射坐标；
- 页面不可见时暂停该路订阅，复用现有`viewers`按需机制。

验收：局域网端到端P95延迟小于300 ms；断线自动重连；开关摄像头不重建RKISP
链路；检测元数据与视频时间戳误差可观测。

### W3：Web推理改为集中调度

Web当前每路按需创建自己的RKNN engine。应复用Qt的`InferenceScheduler`：最多3个
worker、每路一个最新帧槽、round-robin和优先级。无人订阅或检测关闭时取消该路
pending任务，避免恢复后处理旧帧。

### W4：服务端并发和可维护性

- 用线程池或事件循环替代每HTTP连接永久保存一个thread对象；
- 增加连接数上限、慢客户端超时、请求解析限制和结构化JSON；
- 状态接口增加码率、输出尺寸、JPEG/H.264后端、viewer数和最近错误时间；
- 配置热加载只修改安全参数，设备拓扑变更仍通过受控重启完成。

## 4. Qt与Web应共享的模块

建议抽出`zx-camera-core`静态库：

- V4L2设备发现、采集和软暂停；
- DMABUF/RGA转换；
- RKNN engine、集中Scheduler和YOLO后处理；
- 跟踪、时序平滑、性能统计和配置模型；
- 不包含QWidget或HTTP协议代码。

这样Qt和Web只负责呈现层，避免一端修复Start/Stop、另一端仍保留旧状态机。

## 5. 推荐实施顺序

1. Q1：统一遥测与1000轮状态机压力测试；
2. 抽取共享core和测试样本；
3. W3：Web接入集中推理调度；
4. Q2：RKNN输入buffer复用；
5. W1：RGA NV12到MPP的正确硬件编码验证；
6. W2：WebRTC/元数据分离；
7. Q3：UC325硬件解码；
8. 4路、6路、8路逐级压力测试，而不是直接跳到8路。

## 6. 每阶段统一验收表

- 三路画面均可独立及全局开启/关闭；
- 重复Start/Stop无超时、残影和设备busy；
- 检测关闭后NPU任务和旧框均清零；
- J7/J8色彩、曝光和30 FPS原始采集不受影响；
- 无RKNPU、IOMMU、RGA、CSI overflow或RKISP timeout；
- 完整帧可解码，不仅检查文件头；
- 记录CPU/RSS/温度/码率/输出FPS/推理P50-P95/端到端P50-P95；
- 保留一键回退到本次2026-08-06稳定版本的构建产物和配置。
